GETTING STARTED

From a blank project to a finished study.

A walkthrough of the whole path, in order. Each step links to where it happens in the app.

1. Create a project

Open Projects and give it a name. A project starts as an empty shell -- just a recipe file, no netlist -- so it never pretends to be ready before it actually is.

2. Get a real SPICE netlist out of LTspice

This is the step that trips people up most, so read it carefully. With your .asc schematic open in LTspice, either choose View → SPICE Netlist, or right-click an empty spot on the schematic and choose Create Netlist. Either one writes a .net file next to your .asc, containing real SPICE component lines like R1 N001 N002 4700.

Watch out for: LTspice can also export netlists meant for PCB layout tools (for example a file that starts with a header like "ExpressPCB Netlist"). Those describe physical board connections, not a circuit the simulator can run, and look superficially similar at a glance. If System Builder tells you a netlist "must be readable UTF-8 or UTF-16 text" even though the file looks like plain text to you, or preview complains about a missing parameter placeholder no matter what you try, open the file and check: does it actually contain SPICE element lines (R1, C1, Q1, .tran, .ac, .end), or something else entirely?

3. Pick or import the netlist

In Study setup, the Netlist field at the top lists every .cir/.net file already in this workspace. If yours isn't there yet, click ⇧ Import netlist to bring in a file from anywhere on your computer -- it's copied straight into this project's folder and becomes selectable immediately.

4. Turn a fixed value into a variable

A real exported netlist has literal component values (4700), not the {VARIABLE_NAME} placeholders this tool samples over. The built-in editor right below the netlist picker shows that file's text -- delete the literal value you want to vary and click the matching {VAR_NAME} button to insert the exact placeholder syntax at your cursor, then Save netlist. Placeholder names are case-sensitive and must match a declared variable exactly.

5. Declare your variables

In 02 / Variables: a name (matching the placeholder you just inserted), a distribution, a nominal value, and either a tolerance (Gaussian) or a min/max range. This is the manufacturing-variation model -- what a real production run of this part would actually look like, not just its datasheet-typical value.

6. Correlations and corners (optional)

Skip these for a first study. 03 / Correlations links two Gaussian variables that vary together rather than independently (parts from the same reel or batch). 04 / Corners adds named fixed operating conditions -- light load vs. heavy load, for example -- that get crossed with every sampled point, on top of the random variation, not instead of it. See the FAQ for more on both.

7. Set pass/fail requirements

In 05 / Experiments, each analysis needs at least one requirement: a metric (like ac_gain_db or cutoff_frequency), a comparison operator, and a target value. A sampled point only counts as passing if every one of its requirements passes.

8. Preview

Click Preview resolved plan. This only validates and resolves the exact plan -- it never writes a plan file, creates a run directory, or launches LTspice. Fix whatever the errors point at and preview again until it's valid.

9. Freeze, then start

Create immutable plan locks in the exact sample set under a content-addressed plan ID -- it still doesn't run anything. Start local study is the one action that actually launches LTspice, once per sampled point.

10. Read the results

Track progress and open finished reports from Workspace. A completed study's HTML report has plots, worst-case points, and a pass/fail breakdown per requirement -- and lives under runs/ in this workspace as a portable, self-contained artifact.

Optimization (search for a good design point) and Qualification (prove one chosen candidate survives full tolerance) follow this same shape once you have a working Study. See the FAQ for how those relate to each other.

REFERENCE

Frequently asked questions.

What the statistical and workflow terms in this app actually mean.

Sampling

What does "sample count" mean?
How many points get simulated across your declared manufacturing variation. Each point is one complete, independently-parameterized LTspice run. Yield is the fraction of those points that pass every requirement.
Independent random, Latin hypercube, or digit-scrambled Halton -- which sampling method should I use?

Independent random draws every variable independently at random from its distribution -- the simplest, most textbook form of Monte Carlo, but samples can clump together and leave gaps for a small sample count.

Latin hypercube splits each variable's range into as many equal-probability bins as you have samples and guarantees every bin is used exactly once per variable, so coverage is more even than pure random for the same sample count.

Digit-scrambled Halton is a low-discrepancy (quasi-random) sequence: it fills the space more evenly still, and a randomized digit-scrambling step avoids the visible striping artifacts a plain Halton sequence can show in higher dimensions. It's the default and generally the strongest choice for a tolerance study -- it tends to characterize yield accurately with fewer samples than either alternative.

What is a "seed" and why does it matter?
The seed makes sampling deterministic: the same seed, variables, and sample count always produce the exact same sampled points. That's what makes a plan reproducible and its evidence portable -- anyone re-running the same frozen plan gets the identical set of points, not "close enough."

Variables, corners, and correlations

What are "corners"?
Named, fixed operating conditions -- light load vs. heavy load, for example -- rather than randomly sampled ones. Every corner axis you define gets crossed with the entire statistical sample set, so you see manufacturing variation evaluated at each named condition, not a replacement for it.
What are "correlations" for?
Real components from the same manufacturing batch or reel often drift together rather than completely independently. A correlation group links two or more Gaussian variables with a correlation coefficient matrix, so the sampled variation reflects that shared drift instead of assuming every part is an independent random draw.

Plans, workflows, and evidence

Why does "freezing" a plan matter -- isn't Preview enough?
Preview is pure and repeatable, but the recipe backing it can still change. Freezing hashes the exact sample set and netlist content into one content-addressed plan ID -- what actually gets run and reported is always traceable back to that exact, unchangeable definition, so "which version of the recipe did this evidence come from" is never ambiguous.
Study vs. Optimization vs. Qualification -- what's the difference?

Study (statistical/tolerance): does my current design survive realistic manufacturing variation around its nominal values?

Optimization: search a design space for a good -- ideally Pareto-optimal -- nominal design point in the first place.

Qualification: take one specific candidate design (often optimization's winner) and prove it survives full tolerance stackup before you commit to it.

What's a Wilson interval, and why is it next to my yield number?
A confidence interval for the true yield percentage given a finite number of samples. It behaves better than a naive normal-approximation interval, especially when yield is very high or very low or the sample count is small -- which is exactly when a naive interval is least trustworthy.
Where does the evidence from a run actually live?
Under runs/ in the current workspace: LTspice's own RAW waveform files, JSON manifests, CSV exports, and a self-contained HTML report per completed job -- the same portable evidence contract used by the MCP and CLI workflows, not something specific to the GUI.
What metrics can a requirement check?
AC-domain metrics like gain, phase, cutoff frequency, and peaking; transient-domain metrics like rise time, settling time, overshoot, and propagation delay; and general-purpose ones like maximum/minimum. See docs/MCP_REFERENCE.md in the repository for the complete list and exact parameters each metric takes.
